1. Summary

  • MoRI-EP must run GPU-atomic-free on these nodes. The hypervisor enables ACS, so RDMA atomics from the NIC to GPU memory never complete: the atomic build hangs at warm-up round 0 on every ACS-on node. The atomic-free build (PR #736, now in upstream ROCm/mori main from 6731ee1) passes EP16 and EP32 bench, accuracy (2,000/2,000 rounds) and 500K-round stress, and is as fast as the atomic build (within ~2 %).
  • GLM-5.3-Flash-MXFP4 is prefill-bound: scale it with independent EP8 instances, not wider EP. Per-node 2P/2D delivers 172K tok/s at AgentX 512k c64 (TTFT p50 14 s), 1.54× 1P/1D and 1.86× EP16 2P/2D. EP16 is 7–28 % slower than 1P/1D everywhere, with KV usage only 23–30 %.
  • Kimi K3 MXFP4: disaggregation is what makes long-context agents interactive. One TP8 + DCP8 node (the published recipe) serves every context length but decodes at 0.3–0.6 s per token from 512k up. Every disaggregated layout stays at 9–35 ms. TEP8 1P/1D (TP8 attention + EP8, 16 GPUs) is the best expert-parallel recipe at 256k / 512k and at 750k up to c16.
  • EP16 earns its place only where context × concurrency outgrows an EP8 decode node. At 750k c32 TEP8's TTFT p50 reaches 23 minutes. On 128K-in / 8K-out at c64 TEP8 collapses to 126 tok/s with 186 ms TPOT, while EP16 keeps 51–56 ms TPOT at 468–517 tok/s (3.7–4×). EP16 is also the only DP-attention layout that can start at 800K context. But one TP8 + DCP8 node (35.2M-token DCP-sharded cache) still beats EP16 per GPU at every point measured.
  • EP16 over MoRI-EP (atomic-free) is correct at the model level for both models once the configuration rules in sections 3.2 and 8 are followed. GLM-5.3-Flash EP16 2P/2D scores GSM8K in the same 0.887–0.913 band as every EP8 layout and completed its full static and AgentX matrix (prefill batch 4096, GPU util 0.4 / 0.35 with a 16 GiB MoRI heap, --dp-sync-interval 1). Kimi K3 EP16 2P/2D scores 0.938–0.948 (single-node reference 0.940) and serves 750K-token contexts (8 GiB heap, util 0.60). The caveats are settings and throughput, not accuracy.
  • EP16 stability: its prefill deadlocked under long-context load (5 occurrences; GPUs spinning, workers idle). Turning off the ionic CCQE path (MORI_DISABLE_IONIC_CCQE=1) removed it in a direct replica at the same settings. Halving the prefill batch to 4096 is a second workaround (≈ 12 % throughput cost).

3. MoRI GPU-atomic-free (PR #736)

3.1 What changes

  • Upstream MoRI-EP's inter-node dispatch / combine kernels signal completion to remote GPUs with RDMA atomic operations on counters in GPU memory. PR #736 (amirakb89/mori, branch feat/ep-v1-rdma-atomic-free) adds a mode that signals with RDMA WRITE chunk flags instead, selected at runtime by MORI_EP_DISABLE_RDMA_ATOMICS=1 (default off = atomics).
  • Prerequisites (needed by both modes on hosts without a GPU peer-memory client):
    • ROCm/mori#649 registers the Ionic CQ / SQ / RQ rings and the atomic buffer through dma-buf (merged as 15dfb3e0). Without it MoRI-EP cannot create its Ionic queues.
    • ROCm/mori#591 adds MORI_ENABLE_RAIL_ONLY=1, which keeps every RDMA QP on its own rail (ionic_N only reaches ionic_N on other nodes, no cross-rail path).
    • An ionic host driver with dma-buf support (26.08.18 in this work) and the matching libionic GDA userspace provider inside the container (exports ionic_dv_pd_set_dmabuf_alloc).
    All three PRs (#591, #649, #736) are in ROCm/mori main at 6731ee1.
  • Alternative for the atomic build: NIC firmware 1.117.5-a-196 plus PCIe ACS disabled makes RDMA atomics complete under KVM (the original firmware 5a-77 fails even with ACS off). That needs a hypervisor change; the atomic-free mode needs neither firmware nor ACS changes.
  • Why it matters here: with ACS on, NIC→GPU traffic goes through the root complex / IOMMU / VM passthrough. Posted writes survive that path; PCIe AtomicOps do not, so a kernel waiting on an atomically updated counter spins forever. Measured on 13 nodes without exception: on every ACS-off node atomics complete; on every ACS-on node they hang.
  • Cost: none measurable. On ACS-off nodes atomic-free dispatch was ~2 % faster than atomic at 4096 tokens; combine identical (table 3.3).

3.2 How to activate it (upstream)

  1. Build MoRI from upstream ROCm/mori main at or after 6731ee1, which contains PR #736. Released wheels and the stock vLLM ROCm nightly images do not have it (the df6603f0 image ships amd_mori 1.2.3.post1, 2026-09-09), so rebuild MoRI inside the serving image: 
    git clone https://github.com/ROCm/mori.git /tmp/mori-src && cd /tmp/mori-src
git checkout 6731ee1            # or newer main
git submodule update --init --recursive
pip install -r requirements-build.txt cython
MORI_GPU_ARCHS=gfx950 BUILD_TESTS=OFF BUILD_UMBP=OFF pip install . --no-build-isolation
grep -rqs MORI_EP_DISABLE_RDMA_ATOMICS src && echo "atomic-free mode present"
  2. Install the libionic GDA build in the image (section 2) so MoRI can create GPU-side queues over dma-buf.
  3. Runtime environment (every rank): 
    MORI_EP_DISABLE_RDMA_ATOMICS=1          # the atomic-free mode
MORI_ENABLE_DMABUF_REG=1  MORI_ENABLE_RAIL_ONLY=1
MORI_RDMA_DEVICES=ionic_0,ionic_1,ionic_2,ionic_3,ionic_4,ionic_5,ionic_6,ionic_7
MORI_IB_GID_INDEX=1  MORI_RDMA_SL=3  MORI_RDMA_TC=40  MORI_SOCKET_IFNAME=<bootstrap NIC>  GLOO_SOCKET_IFNAME=<bootstrap NIC>
MORI_SHMEM_HEAP_SIZE=8589934592         # 8 GiB; larger heaps starve HIP's free-memory accounting (section 8)
MORI_DISABLE_IONIC_CCQE=1               # recommended for inter-node EP serving (EP16 deadlock, section 6.4)
NCCL_IB_DISABLE=1  HSA_NO_SCRATCH_RECLAIM=1
  4. In vLLM: --enable-expert-parallel --data-parallel-size N with --all2all-backend mori_high_throughput on prefill and mori_low_latency on decode. Keep tokens-per-rank × EP ranks × hidden × 2 B below 2 GiB (larger MoRI-EP inter-node buffers corrupt output); for GLM-5.3-Flash at EP16 that means --max-num-batched-tokens 4096.
  5. Older driver (ionic 26.08.17): GPU CQ creation fails; use the CPU host proxy instead (MORI_ENABLE_HOST_PROXY=1 MORI_DISABLE_IONIC_CCQE=1, within 0–8 % of IBGDA in serving).

6.4 EP16 stability: prefill deadlock and fix

  • Symptom (5 times, AgentX 750k c16 / c32, 256k c32–c64, static c64): a prefill step never completes (RPC call to sample_tokens timed out after 1,200 s). py-spy: every Python worker idle while all 16 GPUs report 100 % busy, i.e. a device-side spin in the MoRI-EP InterNode kernels. DEP8 (MoRI IntraNode) never hung.
  • Fix: MORI_DISABLE_IONIC_CCQE=1. A replica of the run that hung (128K/8K c16 → c32 → c64, prefill batch 8192) completed all cells with CCQE off; 750k c16 also completed, and c32 was running cleanly when the test window ended.
  • Alternative: prefill --max-num-batched-tokens 4096 — 750k c16 + c32 ran ≈ 4.5 h without a hang (16384 hung at c16, 8192 at c32), at ≈ 12 % throughput cost.

7. When EP16 pays off (and when it does not)

RegimeBest layout measuredEP16
Moderate context, any concurrency (GLM all; Kimi K3 256k / 512k)TEP8 1P/1D (K3), per-node EP8 instances (GLM)Slower: inter-node all-to-all on every MoE layer for KV that is not needed
Long context, low concurrency (K3 750k c8–c16)TEP8 1P/1D (≈ 10.5K tok/s, 10–12 ms TPOT, 16 GPUs)Runs (only DP-attention layout that can start at 800K), 21–26 ms TPOT, better prefix reuse and somewhat lower TTFT at c16, but 30–40 % less throughput on twice the GPUs
Context × concurrency beyond an EP8 decode node (K3 750k c32; 128K/8K c32–c64)TP8 + DCP8 single node on throughput per GPUKeeps TPOT at 22–56 ms where TEP8 degrades to 23-minute TTFT (750k c32) or collapses (126 tok/s, 186 ms TPOT at 128K/8K c64); 3.7–4× TEP8's output rate at c64

Reading: EP16 is a capacity tier. Its value grows with context length × concurrent sessions, because its decode pool holds 4–6× what an EP8 decode node holds. On this stack its prefill is limited to TP4 attention per DP rank: the two routes to TP8 prefill (DP2×TP8 per leg; TP8 prefill servers feeding an EP16 decode group) are both blocked in MoRIIO. So EP16's TTFT stays high, and the single TP8 + DCP8 node (35.2M-token DCP-sharded cache) remains the per-GPU leader in every cell measured. EP16 becomes the scale-out choice for agentic long-context fleets once a TP8 prefill can feed it.
