Kimi-K3 1.4 TB MXFP4 — Capacity, Topology & Serving Study for MI300 / MI325

DI-Series blog workbook · why flat DP16/EP16 doesn't fit, what does, and where the time goes · MI325X+Thor2 & MI300X+CX-7 · living doc — updated 2026-09-02
Part of the AMD Disaggregated Inference (DI) Series, which takes frontier open models from a single-node demo to production multi-node serving on AMD Instinct™ GPUs.

Serving a 1.4 TB model is not one hard problem — it is a chain of them, and each link constrains the next. Kimi-K3 is MXFP4, so the instinct is "it's 4-bit, shard it, done." But 7.3% of it never shrinks (the bf16 attention tax), which decides the parallel layout; the layout is forced by the fact that 69 of 93 layers are recurrent and MLA KV cannot be tensor-sharded, which decides how far context can scale; context scaling forces disaggregation, whose KV handoff — uniquely for K3, both latent KV and recurrent state — rides RDMA over two different fabrics that each need their own plumbing. This post follows that chain, with a capacity model you can compute and measurements on two platforms (MI325X+Thor2, 256 GiB and MI300X+CX-7, 192 GiB) where the same config fits one and OOMs the other.

1 · The problem — a 1.4 TB checkpoint that is mostly not 4-bit

Kimi-K3 is a ~2.8T-parameter, 93-layer hybrid-attention MoE (24 full-MLA + 69 KDA layers, 896 routed experts top-16, 2 shared experts). The MXFP4 checkpoint is 1453.7 GiB on disk. The intuition "it's 4-bit, so ÷ down and shard it" is a trap: MXFP4 covers only the routed experts. Attention (MLA+KDA), shared experts, the dense layer, router gates, and the 163,840-vocab embedding/lm_head all stay bf16.

2 · A capacity model you can compute — the wide-EP framing

The key insight (corrects the naïve view). Under wide-EP the 896 routed experts are always EP16-sharded → a fixed 84.2 GiB/GPU, regardless of the attention split. EP is not a free choice — it's invariant. The only free axis is how attention (the 106.5 GiB bf16 remainder) is parallelized: it is replicated per DP rank and divided by TP. So per-GPU weights = 84.2 + 106.5/TP. "DP16 doesn't fit" is really "TP1 doesn't fit," because at TP1 the full 106.5 GiB attention sits on every GPU on top of the 84.2 GiB of experts. Framing + live anchor from MI300X sizing analysis (Confluence 1830010189).

Per-GPU used = 84.2 (experts, EP16) + 106.5/TP (replicated attn) + 16 (MoRI-EP heap) + ~28 (activations/cudagraph/reserve/frag) + KV. The heap and overhead are empirically anchored: the live TP8/DP2 decode pool measures 158.8 GiB/GPU (rocm-smi), which back-solves the non-weight overhead. KDA (69/93 layers) holds fixed-size recurrent state, not per-token KV; only the 24 MLA layers grow KV with context (~13.5 KiB/token fp8).

It is a thin miss, not 7×: the experts already shard fine (EP16), it's the un-sharded 106.5 GiB attention tax that tips it over. Recommendation (theory): TP2/DP8. Not because of memory — TP8/DP2 has more KV room — but because 69/93 layers are KDA recurrent: tensor-sharding them forces a cross-GPU sync on the recurrent state every decode step, while DP keeps each sequence's state GPU-local. Maximizing DP (DP8 = 8 independent streams vs 2) is the biggest throughput lever, and TP2 all-reduce is a cheap 2-GPU xGMI hop. This is the hypothesis the sizing A/B tests. future work: measure TP2/DP8 vs TP4/DP4 vs TP8/DP2 throughput — only TP8/DP2 (158.8 GiB) is measured so far.
Capacity vs throughput are different winners. TP8/DP2 wins KV capacity (least replicated-weight waste → most KV room → best at very-long context). TP2/DP8 wins throughput (8 KDA-local streams). At high context, MLA KV cannot be TP-sharded, so DP-spreading sequences (TP2/DP8) is what holds long contexts on the tighter MI300X — the likely reason #241 defaults to TP2/DP8. The crossover (throughput vs context) is a headline experiment; DCP (decode-context-parallel) is the "can we get both?" third arm.

3 · The serving topology — 2P/2D disaggregated EP16 (TP2/DP8)

This study is disaggregated-only: a dedicated prefill pool and decode pool, EP16 per pool, wired by MoRI-EP (expert all-to-all) + MoRIIO (prefill→decode KV + KDA-state transfer). No pipeline parallelism, no colocated topology. The fixed config everywhere is TP2 / DP8 / EP16 per pool (16 GPUs/pool, 2 nodes × 8).

Why TP2/DP8 (locked). 69/93 layers are KDA recurrent — TP-sharding them forces a cross-GPU state sync every decode step, so DP (state stays GPU-local) is the throughput lever; DP8 = 8 independent streams. TP2 all-reduce is a cheap 2-GPU xGMI hop. And MLA KV can't be TP-sharded, so DP-spreading sequences is what holds long context on the tighter MI300X. One early bring-up check confirms TP2/DP8 loads on MI300X (10 GiB KV room is tight); TP4/DP4 is the drop-in fallback.
K3-specific handoff. K3's hybrid attention makes the disagg handoff heavier than a plain MoE — you ship both MLA latent KV and KDA recurrent state prefill→decode. That is exactly why the mori.rdma.io_transfer profiling and the Thor2 (RoCE) vs CX-7 (IB) fabric comparison are the interesting results.
Figure 3 — 2P/2D disaggregated EP16 topology. Prefill pool (mori_high_throughput, eager) ships MLA latent KV + KDA recurrent state over MoRI-IO RDMA to the decode pool (mori_low_latency, FULL_AND_PIECEWISE). Router = built-in DP-rank round-robin. Fabric: Thor2/bnxt or CX-7/mlx5, both RoCE.

The correctness fix that makes concurrency safe — an RDMA read-after-write barrier

The bug. In MoRIIO WRITE mode, the decode pool admits a request the moment the ZMQ write_done message arrives. But on RoCE, the sender's RDMA-WRITE completing does not guarantee the KV bytes are visible in the receiver's HBM. Under concurrency, decode read stale/garbage KV — distinct-needle NIAH at con=8 recalled only 3/8, with garbled output (not a wrong answer — corrupted state).
The fix (vLLM 2cbc11cd7, +63 lines / 2 files). After the writes complete and before write_done, the producer issues a tiny RDMA read of every written region (readback_targets, capped at 64). An RDMA read-after-write to the same session forces the prior writes globally visible — deterministic, versus a guessed K3_WRITE_FENCE sleep. Gated K3_WRITE_READBACK=1. This was the progression: baseline 3/8 → fence-delay 6/8 (sleep is imperfect) → single-region readback 6/8 (one offset ≠ all KV) → multi-region readback: garbage GONE, every completing request recalls correctly. It is the one functional upstream code change this effort produced; everything else is pinned/consumed unchanged.
Why it belongs in a capacity story. Disaggregation is what buys the context × concurrency envelope (§2, §5) — but it only pays off if the prefill→decode KV handoff is correct under load. The read-after-write barrier is the difference between "the envelope exists on paper" and "you can actually run con=256 without silent corruption." K3 makes this sharper than a normal model: the handoff ships both MLA latent KV and KDA recurrent state, so there is more transferred state per request to get wrong.

The core finding: latency → throughput (the serving envelope)

This stack converts a latency problem into a throughput problem. The disaggregated wide-EP decode carries a fixed per-decode-wave floor (~150 s at 2K ctx; ~605 s at this 2048/128 point) — a flat cost paid once per wave regardless of how little work a request needs. Because it is fixed, not per-request, it amortizes across everything in flight: adding concurrency is nearly free throughput. You do not run this for fast single answers; you run it packed, so the floor is shared across many streams.
Figure 6 — The serving envelope (ISL 2048 / OSL 128). Wall time stays flat while aggregate throughput scales linearly and completion holds at 100% — the signature of a fixed floor being amortized. Every doubling of concurrency doubles throughput at ~constant latency — until the knee at con256→512, where the decode pool saturates: completion falls to 97%, wall hits the 1800 s client cap, and throughput drops (47.6→35.3 tok/s). That is the ceiling of the amortization regime. *con512 wall = client timeout, not true completion time.

Measuring the floor directly — the OSL-intercept experiment

The envelope proves the floor amortizes; this experiment measures it. Hold concurrency fixed (con 8) and sweep only the output length. If a fixed floor exists, wall time is linear in OSL — and the y-intercept (wall extrapolated to zero output) is that floor. It is:

Figure 7 — Isolating the fixed floor. Decode wall vs output length at fixed concurrency fits a straight line wall = 26.6 s + 4.47 s · OSL. The intercept (26.6 s) is the fixed per-wave setup cost; the slope (4.47 s/decode-step) is the recurring all-to-all wave. Both are independent of how many requests share the wave.
The two experiments agree on the same constant — this is the proof. The slope k = 4.47 s per decode-step is per-step, not per-request: every request in a decode wave shares one all-to-all barrier. So throughput ≈ concurrency ÷ k. That equation, fit from the OSL sweep alone, predicts the envelope's independent measurement: con128 → 128 / 4.47 = 28.6 tok/s predicted vs 25.5 measured (11%). The fit is near-perfect: the OSL=256 point lands at 1171.0 s vs the line’s 1171.1 s prediction. Two experiments, different (ISL, OSL, concurrency) shapes, one underlying constant. That is why adding concurrency is nearly free: you are dividing a fixed wave cost across more streams.
This also refines the "~150 s floor" language. The floor is not one number — it is C₀ (setup, ~27 s here) plus k·OSL (the per-step wave). The 150 s seen at the 128/32 point is exactly C₀ + k·32 at that shape. The setup term C₀ itself grows with prefill/KV-transfer size (ISL), which is why long-context points sit higher.

The clincher: AgentX's measured ITL = 4.49 s/token matches the OSL-fit slope k = 4.47 s/decode-step to three significant figures. A completely different methodology — real multi-turn agentic replay via aiperf, versus the synthetic fixed-OSL curl sweep — lands on the same per-decode-step constant. The theory is not an artifact of one benchmark shape.
And it shows the flip side. Because each agentic turn emits hundreds of tokens at ~4.5 s each, a single session takes minutes — in a short benchmark window only one completes. That is the same latency→throughput property viewed from the "unpacked" corner: this stack is built to run packed, amortizing the per-step all-to-all across many concurrent streams, not to serve one fast agentic session. Run it at the concurrency the hardware is sized for and the floor disappears into throughput; run it thin and you pay the floor in full.

The 192-vs-256 divergence, measured. MI300X decode fits at ~170 GiB/GPU (of 192) — the same ~89% utilization as MI325X's 227 GiB (of 256), but with ~22 GiB less absolute headroom per GPU. Since weights + overhead are fixed (~181 GiB base at TP2/DP8), the smaller cap directly shrinks the KV pool → a tighter long-context / high-concurrency frontier, exactly as the capacity model (§2) predicts. Same model, same config, two platforms: the memory frontier is 22 GiB tighter on MI300X.
The frontier is a hard wall, not just a smaller KV pool — the identical config does NOT port to 192 GiB. Live on the real CX-7 cluster with the canonical v4 image: the fabric came up (NCCL world_size=16 cross-node, MoRI RDMA transport OK), weights loaded from NVMe in 144 s, and the capacity readout confirmed 168.8 GiB/GPU mean, 170.3 GiB peak. But then the wall bit: the prefill pool (eager, no cudagraph) survives sitting at 191.9 GiB/GPU — 99.9% of the 192 cap, essentially zero headroom, while the decode pool (FULL_AND_PIECEWISE cudagraph) OOMs during graph capture — HSA_STATUS_ERROR_OUT_OF_RESOURCES, Available Free mem: 26 MB. The 170 GiB of weights + 16 GiB MoRI heap + KV pin leave nothing for cudagraph working memory. On MI325X the same config keeps ~29 GiB/GPU free and captures fine. We then dropped the KV pin to its floor (1.86 GiB) and it still OOMs — the decode-worker init log gives the quantified reason: Initial free memory 172.74 GiB, i.e. only ~17 GiB free per GPU after weights, while K3's 93-layer hybrid stack (24 MLA + 69 KDA) captures two distinct cudagraph families at every capture size, a working set that exceeds ~17 GiB. The KV pin is already minimal; the remaining consumer is graph-capture memory, fixed by layer count — not a tunable. The standard MI325X config (FULL_AND_PIECEWISE decode cudagraph) does not fit 192 GiB. The cause is structural — the fixed 170 GiB weights + 16 GiB MoRI heap against the 64-GiB-smaller cap leave too little for the FULL graph family's capture buffers.
It becomes serveable — but only by downgrading the decode cudagraph. Switching decode to PIECEWISE-only (dropping the memory-hungry FULL whole-model graph family) + shrinking the KV pin (20 GB → 4 GB) brought the full 2P/2D EP16 serve up on MI300X: both pools reached ready, the router came up, and an end-to-end request through the MoRIIO connector returned the correct answer — prefill → RDMA KV transfer → decode all functional on 192 GiB. The only config changes vs the MI325X baseline: DECODE_CG=PIECEWISE and a smaller KV pin. Steady-state VRAM sits at 190.4 GiB of 192 (99%) — it fits on a knife's edge, ~1.6 GiB of headroom. The trade is real: PIECEWISE-only keeps per-layer graphs but loses the FULL whole-model graph, so MI300X runs the identical model at a structurally less-optimized decode path than MI325X. So the honest verdict is not "impossible" — it is "the 192 GiB platform serves K3 wide-EP only by spending the decode-graph optimization the 256 GiB platform keeps for free." The tighter frontier doesn't block the model; it taxes the decode path.

Perf sweeps on MI300X — the cross-platform payoff

With the PIECEWISE serve live, we ran the same envelope + OSL sweeps as MI325X (two 4-node quads in parallel, one per sweep). The results are the heart of the study — same model, same fabric family, two memory sizes:

Figure 8 — MI300X serving envelope (ISL 2048 / OSL 128). Clean throughput scaling to con 64 (18 tok/s), then a hard saturation knee: completion collapses 100% → 75% → 25% → 0% across con 128/256/512. Compare MI325X (Fig 6), which held 100% completion all the way to con 256.
Figure 9 — MI300X fixed-floor fit. Decode wall vs OSL fits wall = 27.3 s + 3.32 s · OSL (predicts OSL 256 = 878 s vs 879 measured). The fixed floor C₀ is 27.3 s — statistically identical to MI325X's 26.6 s.
The two findings that make the cross-platform case.
1. The fixed per-wave floor is platform-independent. MI300X C₀ = 27.3 s, MI325X = 26.6 s — the same ~27 s setup cost on both. That floor is the MoRI all-to-all barrier, a property of the wide-EP collective, not the silicon or the cudagraph mode. The latency→throughput thesis holds on a second platform and a second decode-graph config.
2. Memory vs compute, quantified. MI300X's per-token step is actually faster (3.32 vs 4.47 s/step — newer compute), and its low-concurrency wall is lower (~450 vs ~610 s). But its 4 GB KV pool (forced by the 192 GiB cap) holds ~4× fewer concurrent sequences, so it saturates at con 64 while MI325X scales to con 256. Peak aggregate throughput: MI300X ~18 tok/s vs MI325X ~48 tok/s. The bigger-memory part serves far more concurrent load; the smaller-memory part answers each request a bit faster.

7 · The floor under a real agentic workload — AgentX

Everything above uses controlled ISL/OSL sweeps. The final check asks: does the fixed-floor model survive real traffic? AgentX (aiperf inferencex-agentx-mvp) replays a genuine Claude-Code agentic session trace — the actual think / tool-call / emit token cadence of a coding agent — against the live 2P/2D serve, on each platform independently.

The measured inter-token latency equals the OSL-sweep slope, on both platforms. The per-token latency k extracted from a controlled sweep reappears verbatim when a real agent drives the server — proving C0 + k·OSL is the physical decode mechanism, not a curve fit.

Why 4.49 vs 3.41 — and why it's the same coin as the con64/con256 knee. The AgentX ITL is the per-decode-step time k. MI300X's step is faster (3.32 vs 4.47 s) because at low concurrency each decode step is memory-bandwidth-bound and MI300X wins there — this is not a fabric difference (the C₀ floors are ~equal at ~27 s). The very property that makes MI300X's step faster — few tokens in flight, small KV pool — is exactly what makes it saturate 4× sooner under load (§6). Faster-per-request and lower-capacity are the same fact seen from two angles. On MI325X the ITL held 4.504 s ± 4 ms across 23 independent agentic requests (<0.1% spread) — the signature of a hard floor, not a noisy average.

9 · Takeaways

  • MXFP4 shrinks only the experts. 92.7% of K3 is 4-bit; the other 7.3% (106.5 GiB) is native bf16 attention + embeddings — replicated per DP, ÷TP — and that fixed remainder is what makes TP1/DP16 miss on MI300X and sets the per-GPU floor.
  • EP is fixed; TP/DP is the real dial. Experts always shard EP16 (84.2 GiB/GPU); the only choice is the attention split. TP2/DP8 wins because 69/93 layers are KDA recurrent — DP keeps state GPU-local, TP-sharding would sync it every decode step.
  • Decode is comm/launch-bound (47% all-reduce in the reference profile) — fused collectives are the top perf lever. confirm on MXFP4 disagg decode
  • 192 vs 256 GiB is a real frontier, not a footnote. The same 300K/512K workload holds ~7–8× more concurrency on MI325X than MI300X — the attention tax + un-TP-shardable MLA KV decide it.
  • Long context frays accuracy before it hits the memory wall. On MI325X, 300K recall passes at depth 0.1 but fails at 0.5, and 512K is not even servable (max_model_len 320000). The ceiling is accuracy + the compile window, not just HBM.
  • The serve slows as it ages. The same 300K request took 594 s on a 20-min-old serve and >1200 s on a 90-min-old one — restart fresh before benchmarking (all perf numbers here are from a fresh serve).
  • K3's hybrid KV makes the disagg handoff heavier (MLA latent + KDA state both ship prefill→decode) — the fabric (Thor2/CX-7) matters at the handoff. quantify via mori.rdma.io_transfer
  • Concurrency correctness is a transport problem, not a serving one. The prefill→decode KV handoff needed an RDMA read-after-write barrier (vLLM 2cbc11cd7) to be safe under load — without it, con=8 NIAH corrupted 3/8. The envelope only exists because the handoff was made deterministic (§3).
