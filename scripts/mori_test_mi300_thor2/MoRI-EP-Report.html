1Executive summary

Native MoRI‑EP (GPU‑initiated internode expert‑parallel dispatch/combine over RDMA) and MoRI‑IO (RDMA KV transfer) are both working across the MI300X + Broadcom BCM57608 "Thor2" 400G RoCE fleet. MoRI‑EP initially failed on this NIC; the investigation found two independent blockers, both now resolved. The fix was validated on every node pair in the standardized cluster.

6The problem & the two blockers

MoRI‑EP internode must (a) create a GPU‑resident completion queue via Broadcom Direct‑Verbs, then (b) run a GPU‑initiated all‑to‑all dispatch/combine over RDMA. Two distinct failures sat on this path; MoRI‑IO (pure RDMA WRITE) was never affected by either.

7Root cause #1 — DV‑CQ creation fails on the 237/238 driver

On the 237/238 bnxt drivers, MoRI‑EP aborts the moment it creates its GPU‑resident CQ:

bnxt_re_dv_create_cq_cmd: execute_ioctl() failed: 5
bnxt_re_dv_create_cq: bnxt_re_dv_create_cq_cmd() failed
.../transport/rdma/providers/bnxt/bnxt.cpp:108: Assertion `cq' failed.
kernel: infiniband rocepNNsN: Create HW CQ failed!
        bnxt_re_handler_BNXT_RE_METHOD_DV_CREATE_CQ: Failed to create qplib cq
Root cause (driver source diff, 235 vs 237)
Both drivers ship the CQ‑dmabuf path. The regression is that 237 added a new bnxt_re_setup_cq_hwqs() + cq_timer_reset/cfg step in the DV CQ‑create path that returns EIO on our Thor2 firmware. The 235.2.86.0 driver has none of it and uses the older path that works with the existing firmware — so the fix is driver‑only, with no firmware reflash.

8Root cause #2 — RDMA atomics into GPU VRAM (the real wall)

With the 235 driver the CQ creates, EP advances — process group up, I'm pe 0/1 in 2 pes, Round 0 gen test_data done — then hangs at dispatch. The NIC hardware counters explain why: 

rdma3 (benic4) hw_counters at the hang:
  rx_atomic_requests = 2      # EP dispatch issues RDMA atomics
  tx_atomic_req      = 4
  res_rx_pci_err     = 1      # NIC failed a PCIe access as atomic completer
  unrecoverable_err  = 4
  tx_write_req       = 402    # plain WRITEs flow fine
kernel: infiniband rdma3: bnxt_re_handle_qp_async_event: (user) qp_id 0x401 sq cons 0 rq cons 0

GPU — MI300X (0000:1b:00.0)

AtomicOpsCap: 32bit+ 64bit+ 128bitCAS-

CAN complete 32/64‑bit PCIe atomics

NIC — Thor2 (0000:60:00.0)

AtomicOpsCap: 32bit- 64bit- 128bitCAS-

advertises NO atomic‑completer capability

Mechanism
MoRI‑EP's default v1 / InterNodeV1 kernel posts RDMA AMO_ADD atomics into the peer's GPU‑VRAM counters (token‑count / barrier signalling). The Thor2 NIC must complete those atomics against local GPU‑VRAM across the PCIe root complex — but it has no atomic‑completer capability, so the access errors (res_rx_pci_err), the RC QP goes unrecoverable, and dispatch wedges. Plain WRITEs (what MoRI‑IO uses) are unaffected — which is why MoRI‑IO always worked.

Fix: the async_ll (AsyncLL) kernel signals via RDMA WRITE + poll instead of atomics (the atomic calls are disabled in its source), so it never touches the NIC's missing atomic path.

9The fix

Fix #1 — driver 235.2.86.0

Install bnxt 235.2.86.0 (kernel bnxt_en/bnxt_re + userspace libbnxt_re), reboot. Firmware stays 238.1.138.0.

  • Public debs: packages.broadcom.com/artifactory/ethernet-nic-debian-public/pool/main/
  • Clears the bnxt_re_dv_create_cq EIO

Fix #2 — async_ll kernel

Select the WRITE‑based EP kernel (standalone tests take it on the CLI; vLLM via a small selector patch).

--kernel-type async_ll

GLM top-k = 8 < warpSize 64 (AsyncLL requirement satisfied); prefers MORI_ENABLE_SDMA=1.

11Upstream CI cross‑check — why v1 passes there but not here

The MoRI project's own CI runs a dedicated 2‑node Broadcom (BNXT) internode lane. On the exact commit we tested (12d1bc3), that lane runs every EP kernel — including the default atomic v1/InterNodeV1 — and they all pass. This is the key data point for the escalation: it isolates our issue to hardware/firmware, not MoRI software.

The gap — two orthogonal differences

1. The v1‑atomic gap = the NIC's PCIe atomic‑completer capability — a hardware/firmware property of the specific Broadcom board, not the MoRI code or driver version. The CI runner's Broadcom NIC/fw can complete RDMA atomics into GPU VRAM (AtomicOpsCap 32/64bit+), so v1's AMO_ADD atomics succeed. Our BCM57608‑P2200DQF01 / fw 238.1.138.0 advertises AtomicOpsCap 32bit- 64bit- (verified by lspci) — it physically cannot, so v1 faults (res_rx_pci_err) and hangs. Same MoRI code, same gfx942 — different silicon/fw capability.

2. Why the 237 driver failed for us specifically — a separate, earlier blocker: our 237 driver hit the DV‑CQ‑create EIO (setup_cq_hwqs step) on our firmware 238.1.138.0. The CI runs a different firmware where that CQ path works — so the CI never sees our EIO. We worked around this with the 235 driver.

Why this explanation holds
The CI passes because its Broadcom NIC+fw supports both things our stack lacks: (a) the DV‑CQ‑create path the 237 driver expects, and (b) RDMA atomic‑completion to GPU BAR. The decisive proof it is not a MoRI/software gap: our async_ll result is identical to the CI's async_ll pass — both green. async_ll uses WRITE+poll (never atomics), so it is the portable path that works on both NIC types. On our hardware it is the required kernel; on atomic‑capable NICs it is simply one valid option. (CI uses ROCm 7.2.4 vs our 7.2.3 — not the cause: atomic completion is a PCIe/NIC‑level property, below ROCm.)

13Open items / escalation

  • Broadcom / AMD (NIC — the key ask): the MoRI CI's MI325X_BNXT runner passes the atomic v1 kernel (see §10), so some Broadcom board+fw can complete RDMA atomics to GPU BAR. What board SKU + firmware does that CI runner use, vs our BCM57608‑P2200DQF01 / fw 238.1.138.0 which advertises AtomicOpsCap 32bit- 64bit-? If a firmware exists that flips AtomicOpsCap on our board, v1/v1_ll EP would work here too; otherwise async_ll is the required kernel on our hardware.
  • Broadcom (driver): fix the ≥237 driver's CQ path (setup_cq_hwqs/cq_timer) so it works on this firmware, removing the need to pin 235.2.86.0.
  • AMD / MoRI & vLLM: make async_ll the default / auto‑selected EP kernel for NICs without atomic‑completer capability, so GLM wide‑EP serving selects it automatically on Thor2.
  • Cluster hardware: node node-e is down on a PSU/power‑feed fault (recurring "Power Supply AC lost" in the BMC SEL) — needs a PDU AC‑cycle or physical service; not recoverable from the BMC.
