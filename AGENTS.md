# AGENTS.md

Guidance for coding agents (Claude Code, Cursor, Codex CLI) working in the MAD
repository. Claude Code also reads `CLAUDE.md`, which imports this file and adds
Claude-only notes.

## What MAD is

MAD (Model Automation and Dashboarding) is a curated catalog of AI model
workloads that run on AMD Instinct GPUs via the **`madengine`** CLI. Each model
is one JSON entry in a **per-directory registry**, `scripts/<dir>/models.json`,
or is generated by a `scripts/<dir>/get_models_json.py`. `madengine run --tags <tag>`
builds a Docker image, runs the model in a container, parses a performance
number from stdout, and appends a row to `perf.csv`.

The common tasks here are **benchmarking**, **profiling**, **tuning**,
**adding a model**, **reporting**, and **development** on the repo itself. Each
has a skill in `.claude/skills/`, linked into `.agents/skills/` for Codex
(Cursor reads both):

| Skill | Invocation | What it does |
|-------|-----------|--------------|
| `mad-benchmark` | explicit only | Build and run a madengine benchmark |
| `mad-profile` | explicit only | Profile at the operator, dispatch, or kernel depth |
| `mad-tune` | explicit only | Measure-change-measure tuning loop |
| `primus-projection` | explicit only | Projected memory fit and tokens/s for a Primus training tag only |
| `mad-add-model` | explicit only | Guided model addition and validation |
| `mad-generate-dockerfile` | explicit only | Render a Dockerfile from a framework template |
| `mad-report` | automatic | Summarize or compare benchmark results (read-only) |
| `mad-validate-model` | automatic | GPU-free lint of every registry, its files, and the output contract |

Explicit-only skills build, run, or write files, so agents never pick them on
their own: invoke them as `/<name>` (Claude Code, Cursor) or `$<name>` (Codex).
`.claude/README.md` describes how the skills are shared across the three tools.

### Running madengine from an agent

`madengine run`/`build` take minutes to hours, and agent tool calls time out
(Claude Code ends a call after 10 minutes). Start them through the run helper,
which detaches the run and holds a host-wide GPU lock so concurrent runs queue
instead of sharing GPUs:

```bash
bash .claude/skills/mad-common/mad-run.sh start <run-id> -- madengine run --tags <tag> --live-output
bash .claude/skills/mad-common/mad-run.sh wait <run-id>   # repeat until succeeded or failed
```

`.claude/skills/mad-common/preflight.sh` checks that madengine is installed and
that you are at the repo root. It never installs anything.

## The performance contract (most important convention)

A model's run script MUST print exactly one line to stdout:

```
performance: <value> <unit>
```

madengine greps this line to populate the `performance` and `metric` columns of
`perf.csv`. A run that does not emit it is recorded with no performance value.
Real example (`scripts/huggingface_bert/run.sh`):

```bash
performance=$(grep -Eo "train_samples_per_second':[^,]+" log.txt | sed "s/.*: //g" | head -n 1)
echo "performance: $performance samples_per_second"
```

If a script produces many results, set `multiple_results` in the model's entry to
the CSV filename the script writes (e.g. `"multiple_results": "perf_DeepSeek-R1.csv"`).

## Model registries

madengine discovers models the same way every time:

- the root `models.json` — now just `[]`, but it must exist (madengine requires it);
- every `models.json` found by walking `scripts/` recursively, e.g.
  `scripts/vllm/models.json`;
- every `get_models_json.py` under `scripts/` (dynamic models such as
  `scripts/primus_train`, `scripts/jax-maxtext`). A directory may not have both.

A per-directory model is named `<dir>/<name>` (e.g. `vllm/pyt_vllm_qwen3-8b`);
that is the `model` value in `perf.csv`. `--tags` accepts the bare name, the
`<dir>/<name>` form, any tag, or `<dir>/<tag>` to scope to one directory.
`madengine discover --tags <tag> --json` is the authoritative way to see what a
tag resolves to, with paths resolved. Names must be unique across directories:
madengine would accept a repeated name as `dir/name`, but an unscoped
`--tags <name>` would then select every copy.

Each entry is one object. Paths are **relative to the registry's directory**.
Required fields: `name`, `dockerfile`, `scripts`, `n_gpus`, `owner`, `tags`,
`args` (may be `""`). Optional: `url`, `data`, `training_precision`, `timeout`,
`multiple_results`, `skip_gpu_arch`, `distributed`.

| Field | Notes |
|-------|-------|
| `name` | Unique across all registries. Convention: `{framework}_{project}_{workload}`, e.g. `pyt_vllm_deepseek-r1` |
| `url` | Git repo cloned into the container; `""` if none |
| `dockerfile` | Path prefix relative to the registry dir; engine appends `.ubuntu.amd.Dockerfile`, e.g. `../../docker/pyt_vllm` → `docker/pyt_vllm.ubuntu.amd.Dockerfile` |
| `scripts` | Run script relative to the registry dir, e.g. `run.sh` |
| `n_gpus` | String. `"-1"` = all available |
| `tags` | List; `--tags` matches any tag OR the name |
| `training_precision` | e.g. `fp16`, `bf16`, `fp8`, `fp32`, or `""` |
| `timeout` | Seconds; overrides the 7200s default. `-1` = no timeout |
| `skip_gpu_arch` | Skip on these archs, e.g. `"gfx942"` |
| `args` | Extra args appended to the run script; `--tags <model>:<arg>=<value>` appends `--<arg> <value>` at run time |

Validate after editing (GPU-free): `python3 tools/validation/model_config_validator.py`
checks every registry (or `--model <name>` / `--tag <tag>` for a subset): JSON,
required fields, file references, the Dockerfile header, and the output contract.
CI runs it on every pull request (`.github/workflows/mad-validate.yml`).

## Adding a new model (4 steps)

Use the `mad-add-model` skill, which walks through these steps and validates the result.

1. **Name** it `{framework}_{project}_{workload}`.
2. **Add** an entry to the registry of its script directory: an existing
   `scripts/<project>/models.json` when it reuses a shared runner (e.g.
   `scripts/vllm`), or a new `scripts/<name>/models.json`. Copy the closest
   existing model of the same framework as a template; paths are relative to
   that directory (`"dockerfile": "../../docker/<name>"`, `"scripts": "run.sh"`).
3. **Dockerfile** `docker/<name>.ubuntu.amd.Dockerfile`. First line MUST be the
   context header, then a base image:
   ```dockerfile
   # CONTEXT {'gpu_vendor': 'AMD', 'guest_os': 'UBUNTU'}
   ARG BASE_DOCKER=rocm/pytorch
   FROM $BASE_DOCKER
   ```
   Reuse an existing `docker/*.Dockerfile` of the same stack when possible rather
   than inventing a new base.
4. **Script** `scripts/<dir>/run.sh` that runs the workload and ends by echoing
   the `performance: <value> <unit>` line. Everything it calls must live in
   `scripts/<dir>/`.

Verify GPU-free: `madengine discover --tags <name>` lists it and
`python3 tools/validation/model_config_validator.py --model <name>` passes.
Then on a GPU host: `madengine run --tags <name> --live-output`.

## madengine commands

`requirements.txt` pins madengine to `v2.3.0` (Typer CLI); install it with
`pip install -r requirements.txt`. It exposes five commands: `build`, `run`,
`discover`, `report`, `database`. Verify exact flags with `madengine <cmd> --help`.

- `madengine discover --tags <tag> [--json]` — list matching models (read-only, no GPU); `--json` prints the resolved model cards.
- `madengine build --tags <tag> [-r REGISTRY] [-a gfx942,gfx90a] [-l]` — build images, write `build_manifest.json`. `--use-image` skips the build and uses a prebuilt image.
- `madengine run --tags <tag> [-l/--live-output] [-o out.csv] [--timeout S] [--keep-alive] [--skip-model-run] [-c '<ctx>']` — full build+run (or, with `-m manifest.json`, execution-only). Writes `perf.csv`.
- `madengine report to-html --csv-file-path perf.csv` — HTML report.
- `madengine database -f perf_entry_super.json --db DB -c COLLECTION` — upload CSV/JSON to MongoDB (`-k model,timestamp` sets the unique key; `--dry-run` to preview).

`--skip-model-run` builds the image without running the workload.
`tools/run_models.py` is the **deprecated** legacy runner — prefer `madengine`.

## Deployment target (convention over configuration)

Pass deployment intent via `--additional-context` (a Python-dict/JSON string,
parsed with `ast.literal_eval` so Python dict syntax is fine). The target is
inferred from which key is present:

- `"slurm"` key → SLURM. `"k8s"`/`"kubernetes"` key → Kubernetes. Neither → local Docker.

`docker_env_vars` passes environment variables into the container, and
`docker_mounts` (`{"/path/in/container": "/path/on/host"}`) mounts host
directories.

## Profiling and tracing

Add a `tools` list to `--additional-context`. One depth per run. Do not put
`rocm_trace_lite` and any `rocprofv3_*` tool in the same list.

| Depth | What it answers | Tools |
|-------|-----------------|-------|
| operator | Which PyTorch op or module dominates | `torch_profiler_dynolog` + `tracelens` (`TRACELENS_MODE=pytorch`). Inference sets `TORCH_PROFILE_ITERATIONS=0`. |
| dispatch | Which kernels are on the timeline | `rocm_trace_lite` |
| kernel | Why that kernel is slow | `rocprofv3_compute`, `rocprofv3_memory`, or `rocprofv3_communication` |

```bash
madengine run --tags <tag> --additional-context '{"tools": [{"name": "rocm_trace_lite"}]}'
```

The same three depths cover training and inference. A perf number measured
under a profiler is evidence, not a benchmark score.

Other tool names: `rpd`, `rocprofv3`, `rccl_trace`, `gpu_info_power_profiler`.
Pre-built profiling context files live in the madengine package's
`examples/profiling-configs/`.

## Outputs

- `perf.csv` — one row per run (model, n_gpus, precision, performance, metric, status, durations, git_commit, gpu_architecture, ...).
- `perf_entry_super.json` — enriched record incl. a `configs` block; this is what gets pushed to MongoDB.
