1 What is MAD

MAD (Model Automation and Dashboarding) is a curated catalog of AI model workloads designed to run on AMD Instinct GPUs. Each model is one JSON entry in a per-directory registry, scripts/<dir>/models.json, or is generated by a scripts/<dir>/get_models_json.py (the root models.json is an empty [] that madengine still requires). The madengine CLI handles the full lifecycle: building a Docker image, running the model inside a container, parsing a performance number from stdout, and appending a row to perf.csv.

Claude Code automation sits on top of madengine. Instead of memorizing flags and file conventions, you type a slash command — Claude dispatches the right subagent which constructs and (when a GPU host is available) executes the correct madengine invocation.

User task Slash command Subagent
Run a benchmark /mad-benchmark mad-benchmark-runner
Add a new model /mad-add-model (interactive skill, no subagent)
Profile / trace a model /mad-profile mad-benchmark-runner
Analyze results /mad-report mad-perf-analyst
Tune for better perf /mad-tune mad-tuner
Validate model entries /mad-validate-model (validator script, no subagent)

Two multi-agent workflows handle matrix benchmarking and systematic tuning search: mad-benchmark-sweep and mad-tune-search. These fan out subagent calls and synthesize results into comparison tables. Both plan by default and run on GPUs only with --execute. GPU runs go through .claude/skills/mad-common/mad-run.sh, which detaches each run (a tool call ends after 10 minutes) and holds a host-wide GPU lock, so runs never share GPUs.

Every skill also loads in Cursor and Codex CLI (through .agents/skills/), where it runs inline instead of in a subagent; the workflows are Claude Code only. Skills that build, run, or write files are explicit only in all three tools. Shared conventions live in AGENTS.md; see .claude/README.md.

2 Architecture

The system has three layers: the user interface (slash commands you type in Claude Code), subagents (specialized Claude instances with tool access), and the madengine CLI plus the MAD repository files.

command → agent workflow fan-out agent → engine / files GPU-free path needs AMD GPU

Four of the six slash commands dispatch a subagent; /mad-add-model is an interactive wizard and /mad-validate-model runs a validator script (no GPU). The two workflows fan out to multiple subagent calls (planning runs in parallel; GPU runs execute one at a time) — mad-benchmark-sweep drives the benchmark-runner across a tag matrix, mad-tune-search drives the tuner through operator, dispatch, and kernel profiling, then clean measurements — then synthesizes the results. Agents that need to run madengine always check for AMD GPUs first; if none are present they produce a plan (the exact commands to run on a GPU host) instead of executing.

4 The Performance Contract

This is the single most important MAD convention. Every model's run.sh must emit exactly one line to stdout that madengine can grep. Without it, madengine records the run with no performance value.

Required output — single result
performance: <value> <unit>

For example: performance: 3847.2 tokens_per_second or performance: 124 samples_per_second.

Implementing the line in run.sh

copy# Parse from the workload's own log output, then emit the contract line
performance=$(grep -Eo "train_samples_per_second':[^,]+" log.txt \
  | sed "s/.*: //g" | head -n 1)
echo "performance: $performance samples_per_second"

Alternative: multiple results

When a script produces many rows (e.g. one per concurrency level), have the script write its own CSV and declare "multiple_results" in the model's registry entry (e.g. scripts/vllm/models.json): 

copy# scripts/vllm/models.json entry
{
  "name": "pyt_vllm_deepseek-r1",
  ...
  "multiple_results": "perf_DeepSeek-R1.csv"
}
Hard rule

A run script must satisfy exactly one of the two contracts above. Satisfying neither means madengine records a run with no performance value. /mad-validate-model checks this statically before any GPU run.

Build and run a madengine benchmark for the given tag or model name.

Usage

copy/mad-benchmark <tag-or-model> [extra options]

Examples

/mad-tune command tuner
Iteratively tune a MAD model for better performance using a disciplined measure-change-measure loop.

Usage

copy/mad-tune <tag-or-model> [target: throughput|latency] [lever hints]

Examples

copy/mad-tune bert
/mad-tune pyt_vllm_llama-3.1-8b throughput
/mad-tune pyt_vllm_deepseek-r1 latency try tensor-parallel=4

What the agent does

  1. Reads the model's run.sh, config files, and current perf.csv row to establish a baseline.
  2. Identifies tuning levers for the stack:
    • Env vars: MAD_MODEL_BATCH_SIZE, HIP_VISIBLE_DEVICES, NCCL_*/RCCL_*, PYTORCH_TUNABLEOP_ENABLED
    • Script/config args: tensor-parallel size, precision (fp16/bf16/fp8), sequence length, gpu-memory-utilization, max-num-seqs
  3. Proposes one change at a time, applies it, re-measures, keeps improvements, reverts regressions.
  4. No GPU: produces a ranked list of candidate changes with rationale and the exact madengine run commands to test each.

Expected output

  • Baseline performance value + unit.
  • Table of each change tried with measured delta.
  • Final recommended configuration with before/after numbers.
/mad-validate-model command GPU-free
Statically validate every MAD model registry — JSON, required fields, paths, Dockerfile header, output contract. No GPU required. Works in Claude Code, Cursor, and Codex CLI.

Usage

copy/mad-validate-model [model]

Underlying commands

copypython3 tools/validation/model_config_validator.py                                  # every registered model
python3 tools/validation/model_config_validator.py --tag bert                       # models carrying a tag
python3 tools/validation/model_config_validator.py --model vllm/pyt_vllm_deepseek-r1

Checks performed

Errors (break a run)

  • Every registry parses as a JSON array: the root models.json and every models.json under scripts/; no directory has both models.json and get_models_json.py.
  • Required fields and types (name, dockerfile, scripts, n_gpus, owner, tags, args); names follow the convention and are unique across registries.
  • Dockerfile exists at <dockerfile>.ubuntu.amd.Dockerfile (relative to the registry directory) with the context header in its first 5 lines.
  • Scripts path exists.
  • Output contract satisfied: a performance: line in the script's directory, or the entry sets multiple_results (slurm_multi jobs are exempt).
  • The run fails when no model was validated.

Warnings (non-fatal)

  • Naming consistency between name, tags, and Dockerfile; recommended framework args.
  • get_models_json.py directories not checked when madengine is not installed.
Workflow tip

Run /mad-validate-model <name> after editing a model and before any GPU run (/mad-add-model runs it for you). It catches tag typos, missing files, and missing performance lines in seconds.

6 Workflow Reference

mad-benchmark-sweep workflow
Fan out a benchmark matrix across multiple MAD tags, plan each in parallel or run each one at a time, and synthesize a comparison table. Accepts the same CLI-style flags as /mad-benchmark.

When to use

When you want to compare performance across multiple model tags or GPU counts in one operation.

Phases

Phase 1
Resolve
Expand the sweep matrix into concrete madengine invocations
Phase 2
Run
Plan cells in parallel, or execute them one at a time through mad-run.sh
Phase 3
Synthesize
Parse results into a comparison table with headline finding

Arguments

Accepts CLI-style flags — the same syntax as /mad-benchmark. Pass one or more tags after --tags (comma- and/or space-separated); each tag becomes one sweep cell. A structured JSON object is also still accepted.

FlagMeaning
--tags a,b cOne or more model tags (comma and/or space separated). Required.
--additional-context '{...}'Threaded verbatim into every cell (HF token, docker_env_vars, deployment keys). A per-cell n_gpus is merged in when --ngpus is set.
--ngpus 4,8Optional GPU-count axis — multiplies the matrix (each tag × each count).
--timeout SOptional per-cell timeout in seconds.
--executeRun the cells on this host. Without it the sweep only plans: it resolves tags and prints each command, no GPU. --plan / --no-execute force plan mode.

Example invocations

copy# Plan mode (default) — safe, no GPU required
/mad-benchmark-sweep --tags bert pyt_vllm_deepseek-r1

# Execute — AMD GPU required, context threaded into every cell
/mad-benchmark-sweep --tags bert,pyt_vllm_qwen3-8b --additional-context '{"gpu_vendor": "AMD", "guest_os": "UBUNTU"}' --execute

# GPU-count axis: each tag × each count
/mad-benchmark-sweep --tags bert --ngpus 4,8 --execute
Plans by default

Without --execute the workflow only resolves tags and prints each cell's command; nothing touches the GPUs. With --execute, each cell still self-skips if no AMD GPU is present.

perf.csv isolation

Each sweep cell writes to its own perf_<tag>.csv — never a shared perf.csv, and executed cells run one at a time, so runs never share GPUs. Concatenate the files afterward for a combined report.

Precision is not a sweep axis

In MAD, precision (fp16/bf16/fp8) is fixed per model in its registry entry — it is not a runtime flag. To compare precisions, list the distinct model tags (e.g. pyt_vllm_llama-fp16 and pyt_vllm_llama-fp8) in the tags array instead.

mad-tune-search workflow
Descends operator → dispatch → kernel for a training or inference model, then measures candidates cleanly and sequentially, verifies deltas, and synthesizes the winning config.

When to use

When you want tuning driven by profiling evidence for either a training or an inference model. The search walks three madengine depths, then proposes one-lever changes at the depth that explained the bottleneck.

Core design — one profiler per run, clean runs to measure

Operator is TraceLens on a PyTorch Kineto trace (torch_profiler_dynolog + tracelens). Training counts optimizer.step(). Inference sets TORCH_PROFILE_ITERATIONS=0. Non-PyTorch models skip this rung. Dispatch is rocm_trace_lite, for any HIP workload. Kernel is one of rocprofv3_compute, rocprofv3_memory, or rocprofv3_communication, chosen from the dispatch class. rocm_trace_lite and rocprofv3_* never share a tools array. Baseline and candidate measurements strip tools, because tracing overhead buries the small deltas tuning produces. Primus projection is a separate opt-in (--expect) and stays off by default.

Phases

1
Baseline
Classify training or inference. Clean number, profiler off
2
Operator
TraceLens, PyTorch only
3
Dispatch
rocm_trace_lite timeline
4
Kernel
One rocprofv3 preset
5
Expect
Primus projection, only with --expect
6
Propose
One lever per candidate, citing that depth
7
Evaluate
Clean runs, one at a time, --repeats each, then verify
8
Synthesize
Winning config from trustworthy results

Arguments

Accepts CLI-style flags — the same syntax as /mad-benchmark. Tunes one model; if multiple tags are given, the first is used and the rest are ignored (use mad-benchmark-sweep to compare models). A structured JSON object is also still accepted.

FlagMeaning
--tag NAMEThe model to tune (--tags also accepted). Required; it must resolve to exactly one model.
--candidates NNumber of single-lever candidates, 1–8 (default 4).
--repeats NClean runs for the baseline and for each candidate, 1–5 (default 3). Medians and spread are computed by the workflow; below 2 nothing can be marked trustworthy.
--target throughput|latencyOptimization target (default throughput). Latency treats a lower number as better.
--depth auto|operator|dispatch|kernelDefault auto walks every applicable rung. A named depth runs that rung only.
--profile-tool NAMEForces the matching rung and uses that tool. rocm_trace_lite → dispatch, rocprofv3_* → kernel, torch_profiler_dynolog / tracelens → operator.
--expect / --expect autoOff unless passed. Asks the primus-projection skill for expected tokens/s on a Primus training config. Inference and other trainers skip it.
--additional-context '{...}'JSON or Python-dict context (normalized to JSON; an unparseable value stops the workflow). docker_env_vars, slurm, and k8s are kept. A tools entry is ignored; each depth builds its own. Clean measurements strip tools. For env-lever candidates the agent merges the var into docker_env_vars.
--timeout SOptional per-run timeout in seconds.
--executeMeasure on this host. Without it the search only plans: it prints the madengine commands and ranks candidates, no GPU. --plan / --no-execute force plan mode.

Example invocations

copy# Inference: descend operator (duration capture), dispatch, and kernel, then measure clean.
/mad-tune-search --tag pyt_vllm_qwen3-8b --target latency --candidates 4 --execute

# One rung only
/mad-tune-search --tag pyt_vllm_qwen3-8b --depth kernel --profile-tool rocprofv3_memory --execute

# Primus training, with projection numbers attached
/mad-tune-search --tag primus_train/megatron_MI355X_llama3.1_8B-BF16-pretrain --expect --execute

# Plan mode (default) — print commands, no GPU
/mad-tune-search --tag bert --candidates 4
Sequential evaluation — and why

Candidates are measured one at a time, not in parallel. Running several benchmarks at once on the same GPUs makes them contend for compute and produces meaningless deltas; and candidates that edit run.sh/configs in parallel would race on the same files and clobber each other's apply/revert. GPUs are a serial resource for clean benchmarking, so one-at-a-time is both correct and safe. The cheap adversarial-verify step still runs inline right after each measurement. Each candidate writes its own perf_tune_<id>.csv.

Bottleneck → lever map (best practice)

Dispatch and kernel classify the workload, which decides the levers proposals may use. Training and inference share this table; the family only changes which of those levers exist on the model.

BottleneckProfiling signalLevers to try
Compute-bound GEMM/conv kernels dominate GPU time (e.g. Cijk*, *gemm*, wvSplitK); high occupancy. Signal: rocm_trace_lite/rpd hotspots, rocprofv3_compute occupancy. PYTORCH_TUNABLEOP_ENABLED, hipBLASLt tuning, fp8 / lower precision, larger batch size
Memory-bound Attention / elementwise / norm / copy kernels dominate; low arithmetic intensity. Signal: rocprofv3_memory bandwidth. KV-cache dtype, kernel fusion, gpu-memory-utilization, batch size
Communication-bound RCCL/NCCL collectives (AllReduce/AllGather) are a large share (multi-GPU). Signal: rocprofv3_communication, rccl_trace. NCCL_*/RCCL_* tuning, tensor-parallel vs pipeline-parallel topology
Launch-bound Many tiny kernels with timeline gaps / low GPU utilization. Signal: timeline gaps in rocm_trace_lite. HIP/CUDA graphs, larger batch, fewer sync points

Adversarial verification

The baseline is always measured fresh, --repeats times. Each candidate is measured the same number of times, and the workflow computes the medians, spread, and delta itself. A candidate passes the numeric gate only with at least 2 samples on both sides, the same metric, and an improvement larger than the run-to-run spread (at least 1%). Candidates that pass are then reviewed by a separate subagent, which marks results trustworthy: false if the change was not actually applied, a run used a profiler, or a run failed. The final recommended configuration comes only from trustworthy results.

Set --timeout for long-running candidates

Sequential evaluation means one slow candidate stalls the entire search. Some levers (e.g. PYTORCH_TUNABLEOP_ENABLED) have a pathologically slow first run (online GEMM benchmarking collapses throughput to <1 tok/s). The Docker container launched by madengine outlives the Claude session — if the session ends mid-run the container keeps going but the workflow never completes and a config edit may not be reverted. Always pass --timeout to bound each candidate, and run git status after an interrupted run. During a normal run the workflow checks git status after every candidate and stops the search if an edit leaked. 

/mad-tune-search --tag pyt_vllm_qwen3-8b --timeout 1200 --execute

7 Agent Reference

Agents are specialized Claude instances with a defined tool set and a focused role. They are dispatched automatically by slash commands and workflows — you generally never call them directly.

mad-benchmark-runner agent
Constructs and runs the correct madengine benchmark command from a model/tag or plain-English intent.

Tools: Bash, Read, Grep, Glob

Called by: /mad-benchmark, /mad-profile, mad-benchmark-sweep and mad-tune-search (workflows)

  • Resolves tags with madengine discover (read-only, no GPU).
  • Builds the full madengine run command including profiling context if requested.
  • Checks for GPUs — plan mode if absent, execute if present.
  • Reports resolved models, exact command, required env vars, and output file path.
mad-perf-analyst agent read-only
Reads and analyzes MAD benchmark results from perf.csv and perf_entry_super.json. Never edits files or runs workloads.

Tools: Read, Grep, Glob, Bash (read-only)

Called by: /mad-report

  • Parses perf.csv, perf_entry_super.json, or any named CSV.
  • Summarizes or compares results; precise about units — never compares across different metric values.
  • States direction assumption (higher = better for throughput, lower = better for latency).
  • Uses python3 for parsing — never installs packages.
mad-tuner agent
Iteratively tunes an existing MAD model using a measure-change-measure loop. Reverts regressions automatically.

Tools: Read, Edit, Bash, Grep, Glob

Called by: /mad-tune, mad-tune-search (workflow)

  • Establishes baseline from run.sh, config files, and current perf.csv.
  • Proposes and applies one lever change at a time — keeps improvements, reverts regressions.
  • Requires AMD GPUs to measure. Without GPUs, produces a ranked candidate list with exact commands.
  • Never alters the performance: <value> <unit> output contract.

8 Environment Variables

Pass these environment variables to control model behavior and authentication.

MAD_SECRETS_HFTOKEN
HuggingFace API token. Required for gated models (e.g. Llama 3, Gemma). Set before running any HF model.
MAD_MODEL_BATCH_SIZE
Override the batch size for a model run. Primary tuning lever for throughput experiments.
MAD_RUNTIME_NGPUS
Override the number of GPUs used at runtime (also controllable via n_gpus in the model's registry entry).
MAD_SYSTEM_GPU_ARCHITECTURE
GPU architecture identifier (e.g. gfx942, gfx950). Used for arch-specific builds and skip_gpu_arch filtering.
MAD_MODEL_NAME
Model name passed into the container at runtime. Some scripts use this to select between model checkpoints.
PYTORCH_TUNABLEOP_ENABLED
Enable PyTorch TunableOp for auto-tuned GEMM kernels. A common throughput tuning lever for PyTorch models. First run is very slow (online GEMM tuning collapses throughput to ~0.2–1 tok/s); results are only meaningful on a warm second run with cached kernels. Each madengine run is a fresh container, so the tuned results survive only when PYTORCH_TUNABLEOP_FILENAME points at a host directory mounted with docker_mounts (see the TunableOp tip below).
NCCL_* / RCCL_*
Collective communication tuning (chunk sizes, algorithms, socket buffers). Relevant for multi-GPU runs.
HIP_VISIBLE_DEVICES
Which GPU indices are visible to the container. Use to pin a run to specific GPUs.

9 Tips and Gotchas

GPU guard — plan mode vs execute mode

All agents check for AMD GPUs (rocm-smi or amd-smi) before attempting to build or run. On a machine without GPUs:

  • The agent prints the exact madengine command to run on a GPU host.
  • It lists required env vars (e.g. MAD_SECRETS_HFTOKEN).
  • It stops — it does not attempt to run the command.

GPU-free operations always work: madengine discover, /mad-validate-model, and plan mode for benchmarks and tuning. 

copy# GPU-free: confirm a tag resolves
madengine discover --tags bert
Precision is not a runtime flag

In MAD, training_precision (fp16, bf16, fp8, fp32) is fixed per model in its registry entry. It is baked into the Dockerfile and run script — you cannot change it with a madengine flag at runtime.

To compare precisions in a sweep, use separate model tags that differ in precision. For example: pyt_vllm_llama-fp16 and pyt_vllm_llama-fp8 as two entries in the tags array of mad-benchmark-sweep.

perf.csv isolation in sweeps

The mad-benchmark-sweep workflow gives each cell its own output file (perf_<tag>.csv) and executes cells one at a time, so runs never share GPUs or a perf.csv. After a sweep, concatenate for a combined view: 

copy# Merge sweep results (keep one header row)
head -1 perf_bert.csv > perf_combined.csv
tail -n +2 perf_bert.csv perf_pyt_vllm_deepseek-r1.csv >> perf_combined.csv
madengine report to-html --csv-file-path perf_combined.csv
madengine discover — GPU-free tag validation

Before any GPU run, confirm that your tags resolve to real models. madengine discover reads the model registries without touching Docker or GPUs; --json prints the resolved model cards. 

copymadengine discover --tags pyt_vllm_deepseek-r1
madengine discover --tags vllm   # matches all tags containing "vllm"

The tags field in a model entry supports any-match: madengine selects a model if --tags matches the exact name OR any string in the tags list.

TunableOp: tune once on a host mount, then measure

PYTORCH_TUNABLEOP_ENABLED=1 triggers online GEMM auto-tuning on the first run. During this phase throughput collapses to roughly 0.2–1 tok/s as PyTorch benchmarks every matrix-multiply shape. The actual improvement only shows on subsequent runs using the cached kernel selection.

Measuring TunableOp cold produces a misleading (and huge) regression that the verify step will correctly mark untrustworthy — but only after burning 30+ minutes of GPU time. A warmup run alone does not help: every madengine run starts a fresh container, and --skip-model-run only builds the image, so the results file from one run is gone by the next. Keep it on the host instead:

  • Mount a host directory and point PYTORCH_TUNABLEOP_FILENAME into it (%d becomes the GPU index).
  • Run once with PYTORCH_TUNABLEOP_TUNING=1 to tune. Discard that run's number.
  • Measure with PYTORCH_TUNABLEOP_TUNING=0, so the runs read the tuned results without tuning again.
  • Always set --timeout so a single candidate cannot stall the whole tune-search.
  • The profiling bottleneck data guides whether TunableOp is even worth trying — only relevant for compute-bound (GEMM-dominant) workloads.
copy# 1. Tune (results land in ~/tunableop on the host)
madengine run --tags pyt_vllm_qwen3-8b --timeout 7200 --additional-context '{"docker_mounts": {"/tunableop": "'"$HOME"'/tunableop"}, "docker_env_vars": {"PYTORCH_TUNABLEOP_ENABLED": "1", "PYTORCH_TUNABLEOP_TUNING": "1", "PYTORCH_TUNABLEOP_FILENAME": "/tunableop/results%d.csv"}}'

# 2. Measure with the tuned results, no further tuning
madengine run --tags pyt_vllm_qwen3-8b --additional-context '{"docker_mounts": {"/tunableop": "'"$HOME"'/tunableop"}, "docker_env_vars": {"PYTORCH_TUNABLEOP_ENABLED": "1", "PYTORCH_TUNABLEOP_TUNING": "0", "PYTORCH_TUNABLEOP_FILENAME": "/tunableop/results%d.csv"}}'

Deployment targets — local Docker vs SLURM vs Kubernetes

madengine infers the deployment target from which key is present in --additional-context. No special flag needed. 

copy# Local Docker (default — no key)
madengine run --tags bert --live-output

# SLURM (presence of "slurm" key)
madengine run --tags bert -c '{"slurm": {"partition": "gpu", "nodes": 2}}'

# Kubernetes (presence of "k8s" or "kubernetes" key)
madengine run --tags bert -c '{"k8s": {"namespace": "ml-jobs"}}'
Build-once, run-many pattern

When running the same model many times (e.g. during tuning), build the image once and reuse it to save time. 

copy# Step 1: build only, writes build_manifest.json
madengine build --tags pyt_vllm_llama-3.1-8b

# Step 2: run from manifest (skips rebuild)
madengine run -m build_manifest.json --live-output

# Alternatively: skip the model run but verify image builds
madengine run --tags pyt_vllm_llama-3.1-8b --skip-model-run

Uploading results to MongoDB

Use madengine database to push results to MongoDB after a run.

copy# Dry run first to preview
madengine database -f perf_entry_super.json --db mad_results -c benchmarks \
  -k model,timestamp --dry-run

# Upload for real
madengine database -f perf_entry_super.json --db mad_results -c benchmarks \
  -k model,timestamp

perf_entry_super.json is the enriched record (includes a configs block) that gets pushed. -k model,timestamp sets the unique key for upsert.
